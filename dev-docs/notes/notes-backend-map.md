# Notes Backend Map — Full System Anatomy

> Deep dive into exactly how Notes works, where data lives, what touches it, and where things are broken.

---

## The Big Picture: Two Separate Databases, No Coordination

The system uses **two completely different databases** with no foreign key relationship, no transaction support, and only a loose string tie between them (`userId`).

| Database | What's in it | ORM/Client |
|---|---|---|
| **PostgreSQL** (Neon) | Users, Auth, Cohorts, Lessons, Progress, Chat | Prisma + `@prisma/adapter-pg` |
| **MongoDB Atlas** | Notes, Notebooks, Tasks, Canvas, Workspace settings | Mongoose (raw) |

The `userId` stored in MongoDB is the `cuid()` string generated by Prisma when a user is created. This is the **only thread connecting the two databases**. If a Postgres user gets deleted, their MongoDB workspace document just floats there, orphaned.

## Database 2: MongoDB (All Notes Data)

### File: [`src/server/infrastructure/db/mongodb/client.ts`](file:///d:/ThisPC/Documents/SideQuestHQ/sidequesthq-site/src/server/infrastructure/db/mongodb/client.ts)
### File: [`src/server/infrastructure/db/mongodb/models/UserWorkspace.ts`](file:///d:/ThisPC/Documents/SideQuestHQ/sidequesthq-site/src/server/infrastructure/db/mongodb/models/UserWorkspace.ts)

**Connection:** `global.mongooseCache` singleton pattern (lines 23–27). `connectToMongoDB()` is called at the start of every repo method — not a middleware, not a connection pool manager. Every function that touches the DB manually awaits this.

### The `UserWorkspace` Document (One Document = One User's Entire Workspace)

```
UserWorkspace {
  userId: string          // ← Postgres User.id (cuid string, NOT a Mongo ObjectId)
  settings: {
    theme: 'light'|'dark'|'system'
    sidebarOpen: boolean
  }
  canvases: ICanvas[]     // Excalidraw drawing data (can be HUGE)
  notebooks: INotebook[]  // All user's notebooks
  notes: INote[]          // ALL notes for ALL notebooks, flat array
  tasks: ITask[]          // Floating tasks (attached to noteId)
  aiMemory: {}            // Unused JSON blob
  recentViews: string[]   // Bounded to 100 items
  createdAt, updatedAt    // Mongoose timestamps
}
```

> [!CAUTION]
> **Everything for a user is in ONE MongoDB document.** All notebooks, all notes, all tasks, all canvases — one giant doc. No sub-collections, no separate documents per note. This is the core architectural problem.

**Sub-schemas (all with `_id: false` — no per-element Mongo IDs):**

| Schema | Key fields | Line |
|---|---|---|
| `NotebookSchema` | id (client-generated), title, color, icon, order, favorite, shared, archived, collapsed | L86 |
| `NoteSchema` | id (client-generated), notebookId, title, content, contentType, kanban*, elements* | L101 |
| `TaskSchema` | id, noteId, title, label, dueDate, status, priority | L123 |
| `CanvasSchema` | id, elements (Mixed), appState (Mixed) | L79 |

**All IDs are client-generated strings** (not Mongo ObjectIds). The `id` field on each sub-document is created in the browser via `\`${prefix}-${Date.now()}-${Math.random()}\``.

## Authentication Bridge

### File: [`src/server/infrastructure/auth/auth.config.ts`](file:///d:/ThisPC/Documents/SideQuestHQ/sidequesthq-site/src/server/infrastructure/auth/auth.config.ts)
### File: [`src/server/infrastructure/auth/getUser.ts`](file:///d:/ThisPC/Documents/SideQuestHQ/sidequesthq-site/src/server/infrastructure/auth/getUser.ts)

**Auth:** NextAuth v5, JWT strategy, `PrismaAdapter` (sessions stored in Postgres).

`getUser()` is a 3-line function that calls `auth()` (NextAuth) to get the JWT session and returns `session.user`. The `user.id` here is the Postgres `cuid`. This is the key passed into every MongoDB query.

**How the bridge works:**
1. User logs in → NextAuth creates/finds them in Postgres `users` table
2. JWT is issued with `token.sub = user.id` (Postgres cuid)
3. Every API route calls `getUser()` → gets that `user.id`
4. That `user.id` becomes `userId` in MongoDB queries

## API Layer: The Notes Endpoint

### File: [`src/app/api/workspace/notes/route.ts`](file:///d:/ThisPC/Documents/SideQuestHQ/sidequesthq-site/src/app/api/workspace/notes/route.ts)

Only **two HTTP methods**, handling everything:

### `GET /api/workspace/notes`
1. `getUser()` → validates session
2. `WorkspaceRepository.getNotesState(userId)`
   - Fetches the FULL UserWorkspace doc from Mongo
   - Returns `{ notebooks, notes, tasks, selectedNotebookId: null, ... }`
3. If no workspace exists → returns a **hardcoded default state** (one notebook: "SideQuestHQ diary") — inline in the route handler (lines 12–36), not in a service or config file

### `PATCH /api/workspace/notes`
1. `getUser()` → validates session
2. Takes raw `body` — no validation, no schema, no zod
3. `WorkspaceRepository.saveNotesState(userId, body)` → overwrites `notebooks`, `notes`, `tasks` arrays entirely
4. Returns the body back as-is

> [!WARNING]
> `PATCH` accepts **any JSON body** and writes it directly to MongoDB. No input validation, no type checking, no sanitization. A malformed client payload can corrupt the entire workspace document.

## Client-Side Layer

### State Management

The **entire notes state lives in React state** (`useState`), not in a global store (no Zustand, no Redux, no Context). The root hook is `useNotes`.

### File: [`src/client/screens/dashboard/notes/hooks/useNotes.ts`](file:///d:/ThisPC/Documents/SideQuestHQ/sidequesthq-site/src/client/screens/dashboard/notes/hooks/useNotes.ts)

The single source of truth for all note/notebook state on the client.

**Two `useEffect`s control the persistence loop (lines 26–31):**
```ts
// Load on mount
useEffect(() => {
  notesRepository.load().then(setState);
}, []);

// Save on EVERY state change
useEffect(() => {
  if (state) void notesRepository.save(state);
}, [state]);
```

> [!CAUTION]
> **Every single state change triggers a full PATCH to the server.** Select a different notebook? PATCH. Type a character in a title? PATCH. Move a note? PATCH. This sends the ENTIRE `{ notebooks, notes, tasks }` blob on every change. No debouncing, no diffing, no batching.

**All mutations are pure functions** that call `setState` via the `update()` wrapper. IDs are generated client-side with `id()` helper (line 15). Timestamps are generated client-side with `stamp()` (line 14).

**Undo mechanism (lines 57–70):** Stores last deleted notes/notebooks in `lastDeleted` state. One level deep — one undo operation max.

**`confirm()` dialogs in business logic (lines 147, 220, 254, 286):** Delete and archive actions call `window.confirm()` directly inside state update functions. These are blocking browser dialogs from inside a `useCallback`.

### File: [`src/client/screens/dashboard/notes/repositories/notes.repository.ts`](file:///d:/ThisPC/Documents/SideQuestHQ/sidequesthq-site/src/client/screens/dashboard/notes/repositories/notes.repository.ts)

Thin fetch wrapper. `load()` → GET, `save()` → PATCH. No caching, no retry logic, no optimistic updates. On error, `load()` returns an empty state (silent failure).

### File: [`src/client/screens/dashboard/notes/models/notes.models.ts`](file:///d:/ThisPC/Documents\SideQuestHQ/sidequesthq-site/src/client/screens/dashboard/notes/models/notes.models.ts)

- `publicLink: boolean` in client model vs `publicLink?: string` in Mongoose schema

## Canvas Persistence (The Second System)

Canvas data has a **completely different persistence story** from notes metadata.

### Two-tier storage:
1. **`localStorage`** — primary canvas storage (in browser), max 10MB per note
2. **MongoDB `canvases[]`** — secondary cloud backup (via `POST /api/workspace/canvas`)

### File: [`src/client/screens/dashboard/notes/repositories/canvas.repository.ts`](file:///d:/ThisPC/Documents/SideQuestHQ/sidequesthq-site/src/client/screens/dashboard/notes/repositories/canvas.repository.ts)

localStorage wrapper with two keys per note:
- `sidequesthq.canvas.<noteId>` — primary key
- `sidequesthq.canvas.backup.<noteId>` — emergency backup (written synchronously on every change)

Implements a **partial save fallback**: if serialized scene exceeds 10MB, strips image files largest-first until it fits.

### File: [`src/client/screens/dashboard/notes/hooks/useCanvasScene.ts`](file:///d:/ThisPC/Documents/SideQuestHQ/sidequesthq-site/src/client/screens/dashboard/notes/hooks/useCanvasScene.ts)

On every `handleSceneChange` (Excalidraw callback):
1. Immediately writes to localStorage backup (sync, never throws)
2. Marks dirty state
3. Triggers `saveTrigger` increment (for `useCanvasPersistence`)
4. Calls `saveToDb()` — debounced 1000ms — which POSTs to `/api/workspace/canvas`

### File: [`src/client/screens/dashboard/notes/hooks/useCanvasPersistence.ts`](file:///d:/ThisPC/Documents/SideQuestHQ/sidequesthq-site/src/client/screens/dashboard/notes/hooks/useCanvasPersistence.ts)

Debounced 1500ms localStorage save (separate from the DB save above). On unmount while dirty: flushes both localStorage and attempts API save.

> [!WARNING]
> Canvas has **three parallel save paths**: (1) immediate localStorage backup on every keystroke, (2) debounced 1500ms localStorage primary save, (3) debounced 1000ms API (MongoDB) save. These are not coordinated. A crash between saves means localStorage has data the server doesn't.

## Full Request Flow: Opening Notes

```
User opens /notes page
  → NotesDesktop.tsx mounts
    → useNotes() initializes
      → useEffect → notesRepository.load()
        → GET /api/workspace/notes
          → getUser() → auth() → JWT → user.id
          → connectToMongoDB() (or use cached conn)
          → UserWorkspace.findOne({ userId }).lean()
          → Returns { notebooks, notes, tasks, selectedNotebookId: null, ... }
        → setState(result)
      → useEffect (state dep) fires immediately after setState
        → notesRepository.save(state)  ← IMMEDIATE PATCH ON LOAD
          → PATCH /api/workspace/notes (writes same data back)
```

> [!CAUTION]
> Every page load triggers both a GET and a PATCH. The save `useEffect` fires whenever `state` changes, including the initial `setState` after loading. This means opening the page always writes to the DB.

## Full Request Flow: User Changes a Note Title

```
User edits note title (keypress)
  → actions.patchNote(noteId, { title: newTitle })
    → setState (immutable update)
      → useEffect [state] fires
        → notesRepository.save(fullState)
          → PATCH /api/workspace/notes
            → WorkspaceRepository.saveNotesState(userId, body)
              → UserWorkspace.updateOne(
                  { userId },
                  { $set: { notebooks: [...], notes: [...], tasks: [...] } }
                )
              // Sends the ENTIRE notes array (all notes, all content) on every keystroke
```
