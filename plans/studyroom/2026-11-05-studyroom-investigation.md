# Studyroom investigation — 5 November 2026

## Investigation plan

1. Trace discovery, creation, invitation, admission, exit and authority changes through persistence.
2. Compare server permissions with controls, subscription grants and multi-user state updates.
3. Inspect retry, reconnect, concurrency, deployment and idle/active work. Run isolated checks.
4. Record evidence, cost assumptions, gaps and closure criteria.

## Verdict

**Hold release for multi-user use.** Room creation has transactional provisioning, and the realtime authorization proxy checks membership and live leases. Those protections cover only part of the journey. A fresh room mount can throw, a warm mount can repeatedly subscribe, a fresh host can join without receiving host controls, and an authenticated outsider can retrieve a private cohort sprint's participant names. The last case is reachable directly over HTTP, independently of the room UI.

Assessed the initially clean working tree on master at `3aab4162`, Node 24.14.1, Vitest 4.1.11. Scope was the current web implementation, its HTTP entry points, PostgreSQL persistence, realtime integration and recurring cost. Findings describe this revision. Historical introduction is unknown. No production data, infrastructure or application code was changed.

**Evidence strength.** 559 repository tests passed across 65 files. Ten additional reproductions exercised production components, hooks, routes or services against isolated fixtures. These establish specific failures. The Docker Linux engine was unavailable and the usual local app, PostgreSQL, Redis and Centrifugo ports had no listener. Two authenticated browsers backed by the full stack, production latency, production data exposure and actual invoices remain unverified. The report separates conditional database interleavings from reproduced failures.

## Coverage and expected authority

Paths below are repository-relative. Client hook references are under `src/client/screens/dashboard/studyroom/hooks/`, room UI under `src/client/screens/dashboard/studyroom/`, domain services under `src/server/domain/studyroom/`, and room HTTP routes under `src/app/api/studyroom/`.

| Journey | Operation traced | Disposition |
|---|---|---|
| R1 Create and manage | Discovery → CreateRoomModal → POST rooms → quota/cohort policy → transaction creates room, channel, stream, environment and audit → draft or immediate navigation | Ordinary create has all five writes in one transaction. Invalid scope, retry, draft management and quotas fail in cases below. |
| R2 Join and leave | Card/shared slug → dashboard route → bootstrap → join with tab ID → participant and lease → roster → renewal, leave, switch or timeout | Single-user service checks exist for lifecycle, cohort, restrictions and capacity. Mount, direct link, concurrent admission and stale leases break the full journey. |
| R3 Change authority | Owner assigns/revokes host/moderator, proposes/cancels transfer, recipient accepts, moderator removes/bans, manager reads restrictions/audit | Database role and audit writes exist. Client authority can lag indefinitely. Some API permissions diverge from policy. |
| R4 Peer updates | Manifest and subscription proxy → room/chat/user streams → transactional event and delivery → dispatcher → roster, scene, sprint, chat or personal timer | Normal event producers and consumers exist. Subscription lifecycle and missed-event recovery fail. A peer can keep a cleared soundscape. |
| R5 Cost | Per-tab timers, focus and join fan-out, DB reads/writes, outbox and lease cleanup, load harness | Predictable idle request counts and query amplification. Actual costs and maximum sustainable occupancy require measurement. |

| Actor | Intended capabilities from policy and server entry points | Material discrepancy |
|---|---|---|
| Anonymous / shared guest | Limited preview. Normal admission and room control require an eligible account. | Discovery and bootstrap can expose private room data. Malformed create scope skips the branch containing the guest and quota checks. |
| Eligible signed-in viewer / participant | Join an open room within capacity, see peers, chat, participate in a sprint, publish own goal, leave. Personal tasks and Pomodoro belong to that user. | Stale participant rows satisfy some active-membership checks. A newly joined viewer keeps the pre-join capability projection. |
| Host | Participant privileges plus shared environment and sprint control while present. | Fresh host lacks these controls in the UI. A direct control request can succeed without a live lease. |
| Moderator / cohort governor | Control shared activities and remove/ban lower-ranked members. Owner retains role assignment and room settings. | Moderators see a role-assignment action the API denies. Roster labels omit inherited cohort authority. |
| Durable owner | Settings, lifecycle, delegated roles, moderation, proposing ownership transfer. Only designated recipient accepts. | Draft/closed management is inaccessible from the ordinary room link. Transfer state and previous-owner controls can be stale. |
| Platform admin | Policy supports an admin override when trusted platform role is supplied. Ownership handoff remains owner-specific. | Normal bootstrap explicitly passes null and representative management calls pass user ID alone. A platform admin lacking local authority does not receive the modeled override. |

The shared state contract includes presence, published goal, selected scene/soundscape/music source, group sprint and chat. Personal mute, playback controls, tasks and a user's own timer need separate tests. Personal timer events use a user channel. Exact audio playback position across devices is outside the implemented shared-source contract.

## High severity findings

**H01 · Direct room mount throws and warm navigation can churn subscriptions.** Reproduced both paths. RoomScreen.tsx:125–150 calls useSharedEnvironment with a room ID or slug during loading. Its effect at useSharedEnvironment.ts:106–123 acquires a subscription before the parent provider's connect effect installs a client. The actual registry throws. With an already mounted provider, acquire and release each set a fresh activeChannels array, changing the context object that the effect depends on. A bounded reproduction exceeded 12 renders for the same room without a user action. See `src/client/realtime/RealtimeContext.tsx:52–56,147–178,201–216` and `subscription-registry.ts:38–73`. Roster, sprint, chat and personal timer also depend on the whole realtime object. Gate subscriptions on client readiness and authorization, depend on stable methods, and emit channel-list changes only when membership changes. Verify both direct load and dashboard navigation with the real provider, count subscriptions over idle time, then disconnect/reconnect once.

**H02 · An invalid discovery tab exposes listed private-cohort rooms.** Reproduced through GET with anonymous fixtures. `route.ts:23–55` casts arbitrary input. `room-discovery.service.ts:47–121` applies membership predicates inside known tab branches. For `?tab=invalid`, the query contains only OPEN and LISTED. Its projection includes room, owner and cohort details. Apply an allowlist at HTTP entry and scope by viewer independently of tab. Repeat with unknown, empty and valid tabs as anonymous, unenrolled and enrolled users.

**H03 · Room details and sprint identities cross the admission boundary.** Reproduced two independent reads. Anonymous bootstrap for a listed private-cohort room returned its configured music URL alongside canJoin=false. A signed-in outsider using the room ID received a paused sprint and participant name with HTTP 200. Bootstrap serializes environment, owner data, rules and sprint details after evaluating eligibility (`[roomSlug]/route.ts:12–24`, `room-management.service.ts:557–589,637–714`). Environment and sprint GETs check account/guest and room existence. Sprint snapshot includes participant IDs, names, usernames and images (`[roomSlug]/sprint/route.ts:18–37`, `environment/route.ts:23–40`, `sprint.service.ts:544–624`). The page metadata also looks up the title by slug/ID without audience checks. Define a minimal preview projection, then require authorized room access before loading private state. Exercise denied anonymous, outsider, banned, closed and expired-lease cases directly against each endpoint.

**H04 · Create quota and guest checks can be skipped with a malformed scope.** Reproduced HTTP 201 for an over-quota fixture using scopeKind=TYPO. The same actor was denied with STANDALONE. `rooms/route.ts:8–17` passes raw JSON. `room-management.service.ts:130–160,187–206` checks two recognized branches, then writes cohortId=null for other values. Guest rejection lives inside the skipped standalone quota policy. Cohort creates also bypass the daily count, and PUBLISH/REOPEN skip the three-open-standalone limit (contracts.ts:41–42, room-management.service.ts:385–417). Reject invalid scope and enforce account, daily and open-room limits at each applicable transition under concurrency. Test malformed scope, draft → fourth open room, and simultaneous requests.

**H05 · Unlisted share links strand first-time visitors.** CreateRoomModal.tsx:216 labels this option “Unlisted (Direct link only)”. RoomSocial.tsx copies the canonical URL. Bootstrap at room-management.service.ts:581–589 returns 404 unless the visitor already has a lease or is owner/admin/moderator. The client requires bootstrap before it can join (useRoomOrchestration.ts:141–185). Even a delegated HOST without a lease misses the exception. Direct join applies no corresponding listing check. Decide the invitation contract explicitly and enforce it identically at bootstrap and join. Verify a fresh invited account, a shared cohort link used by a nonmember, and an unlisted room's absence from discovery.

**H06 · Draft, closed and archived room management is unreachable through the normal UI.** Draft and closed admission is denied (studyroom.policy.ts:214–222). RoomCard.tsx:156–164 links into the stage, which returns the denial view before mounting settings (RoomScreen.tsx:410–477,665 onward). An owner saving a draft cannot publish it there. An owner closing a room loses the same route to reopening it. My Rooms excludes ARCHIVED and the dynamic page excludes archived DB rows, so RESTORE is similarly stranded for ordinary custom slugs. Separate management access from seat admission. Exercise draft → publish → close → reopen and closed → archive → restore entirely through the UI.

**H07 · Controls and role changes do not converge for people already in the room.** Reproduced a fresh delegated host reaching joined with canControlEnvironment=false. Bootstrap computes this bit from a pre-join lease. Successful join sets generation and refreshes a manifest whose response is discarded. The client keeps the original bootstrap (useRoomOrchestration.ts:144–192,476 onward, RoomScreen.tsx:131–148). Assignment/revocation and ownership proposal/acceptance write controller/transfer and audit records without delivering a capability invalidation (room-governance.service.ts:107–174,554–590,658–689). Roster polling updates other people's rows, not the viewer's bootstrap or pending-transfer banner. Return post-join capabilities and send a targeted governance invalidation on every committed change. Verify promotion, demotion, proposal, cancellation and acceptance on both clients without reload, including loss of authority on the former owner.

**H08 · The server allows shared controls after departure or moderation.** Reproduced an owner with zero live leases updating the environment. The policy has a live-lease assertion, but environment.service.ts:164–175 and sprint.service.ts:83–165,347–469 use a separate role-only check. Kick/ban removes leases and presence while retaining delegated roles. A banned host retaining a controller row can consequently issue control requests. Use the same current room, eligibility, active lease and role predicate across control writes. Check direct HTTP after host exit, ban, demotion and room closure, including an old open tab.

**H09 · Multiple endpoints resolve the wrong room or fail after a rename.** Reproduced a stored slug missing its renamed room. sprint.service.ts:63–77 tries ID then loads every room and compares a title-derived slug. The canonical page and bootstrap use the stored slug. Duplicate titles with suffixes also fail this fallback, and a different room whose title now matches can be selected. Controllers, moderation, transfers, audit, sprint and environment routes reuse the resolver (e.g. controllers/[userId]/route.ts:19–30). Replace it with an indexed ID/stored-slug lookup, with explicit legacy mapping only where necessary. Test duplicate titles, renamed rooms, and two rooms with swapped titles.

**H10 · Last-seat admission and lifecycle exclusion have no shared serialization point.** Under ordinary PostgreSQL Read Committed isolation, two different users can both count one free seat before either writes. Eligibility counts with the global Prisma client (studyroom.policy.ts:295–314), and join later upserts presence and lease (studyroom.service.ts:336–363,510–559). The reads described as locks at 434–437 are plain findUnique calls during switching. A join can similarly read OPEN before a close commits and write presence after eviction. Distinct-user uniqueness protects one identity, not room capacity. Conditional concurrency finding, not a measured production oversell. Serialize admission with lifecycle per room, recheck membership/capacity inside that boundary, and race independent DB connections against one remaining seat and a simultaneous close. The local Prisma client sets wait/timeout only. [PostgreSQL transaction isolation](https://www.postgresql.org/docs/current/transaction-iso.html)

**H11 · Revision and ownership checks do not guard the final write.** Settings and lifecycle check the revision then update by ID alone (room-management.service.ts:295–326,376–451). Environment similarly reads and then updates by room ID (environment.service.ts:201–223). Transfer acceptance checks recipient, pending state, expiry and room revision before the transaction, then unconditionally updates the owner and transfer (room-governance.service.ts:619–680). A cancellation can win after validation and still be overwritten by acceptance. Two editors can both receive success on the same starting revision. Make revision, sender/current owner and pending status conditions of the writes and roll back on a miss. Verify exactly one winner for competing edits and mutually exclusive cancellation versus acceptance.

**H12 · Missed room events do not reliably repair peer state.** useRoomOrchestration.ts:315–467 syncs on a sequence gap only after a nonzero cursor. It accepts the first high sequence, advances snapshots without hydrating environment/sprint, and replays deltas through a handler that ignores those event types. The server delta window can be 150 with a default page of 100 (studyroom.service.ts:1195–1245). No loop consumes the remainder. Chat history is fetched on mount or manual refresh, separately from gap repair (useRoomChat.ts:57–146). Live chat subscription uses the room generation, while the manifest and proxy use the independently versioned chat stream (RoomScreen.tsx:545–557, manifest.service.ts:165–183). Bootstrap cursors and rehydrate authoritative state after reconnect or an unrecoverable publication. Verify missed final updates in a quiet room, 120 missed events, and distinct room/chat generations.

**H13 · Expired membership can continue to grant access and be renewed.** No running caller for reconcileExpiredLeases was found in repository code. Chat history falls back to a participant row when no live lease exists (`src/app/api/community/channels/[channelId]/messages/route.ts:207–229`), sprint join also accepts a participant row (sprint.service.ts:258–277), and renew upserts a lease after checking only assignment/generation (studyroom.service.ts:667–706). Abrupt tab loss leaves a row that can still read history, and a delayed renewal can bypass fresh eligibility, even after cohort membership changes. The subscribe proxy itself checks live expiry. Enforce the live lease at protected operations, use a fresh admission check after expiry, and wire bounded cleanup. Kill a browser, wait past 90 seconds, remove cohort membership and exercise HTTP and websocket paths.

**H14 · A runtime denial can still render the active room.** A kick/ban/closure or proxy authorization error sets orchestration state to denied but retains the earlier ELIGIBLE bootstrap. The stage's return guard requires both denied and an ineligible reason (RoomScreen.tsx:89–101,410–477). A bootstrap-level 403 with no stored reason also misses this branch. RoomSocial can keep a channel ID, and environment subscription is independent of membership. This is a UI/state exposure after denial. Continued server reads depend on the endpoint's own checks. Render denial from authoritative state, clear cached private state and detach protected subscriptions immediately. Verify kick, ban, close and 403 after a previously successful join, with both browsers open.

## Medium severity findings

**M01 · Repeated create can duplicate a room.** CreateRoomModal.tsx:71–85 generates a new request ID on each submit. Lose a successful response and retry, and room-management.service.ts:55–85 cannot replay the first transaction. The slug collision logic allows another room. The audit-key lookup is also separate from insert with no unique actor/action/request constraint in the foundation SQL. Persist the same ID for the same user intent and claim it atomically. Test a dropped response and simultaneous retries.

**M02 · Leave omits the generation fence.** The repository and unload beacon send room/tab without generation (studyRoomRepository.ts, leaveRoom, and useRoomOrchestration.ts:210–247). The server applies generation fencing only if supplied (studyroom.service.ts:723–770). A delayed leave from A → B → A in the same tab can evict the new A lease. Require a generation for tab leave and constrain the delete by that generation and room. Replay an old beacon after re-entry.

**M03 · Room goals disagree across server instances.** Public goals use a process-local map updated before the outbox transaction (studyroom.service.ts:43,278–280,892–925). Peer B can receive a public goal via an event and lose it on the next roster fetch served by another process. Clearing it on one process leaves a stale published goal on another. Persist the visible goal against the current assignment and commit its event in the same transaction. Alternate requests between two instances across publish, hide, switch and restart.

**M04 · Shared environment can silently diverge.** Reproduced a peer with rain retaining rain after an authoritative null soundscape. useSharedEnvironment.ts:55–73 uses a fallback on null and does not reject old revisions. At 126–156, non-409 write errors are swallowed after the local UI has changed. Slower old snapshots and requests that fail with 403/429 can leave two users seeing different settings. Apply explicit clears, ignore old revisions and reconcile or surface failed writes. Test rapid edits by two controllers, a rejected write and clear while both clients are connected.

**M05 · Role controls and labels disagree with server policy.** ParticipantActionsMenu.tsx:131–174 displays Make/Revoke Host to anyone with canManageParticipants. Only owners can assign/revoke controllers (room-governance.service.ts:75–89,143–157). Peer moderators can also be offered actions their rank forbids. Roster projection recognizes the direct owner and delegated rows only (studyroom.service.ts:258–280), omitting an inherited cohort moderator. The server has list/delete restriction endpoints but the stage offers a ban action without an unban/list flow. Use per-action capabilities and canonical role projection, and expose ban reversal to authorized managers. Verify owner, peer moderators, host and participant controls separately.

**M06 · Platform admin authority is lost between HTTP and policy.** studyroom.policy.ts:63–70 requires an explicit platformRole argument to recognize ADMIN. Bootstrap passes null, and management/governance calls resolve with the actor ID alone (room-management.service.ts:288–295,573–580 and room-governance.service.ts:75–80). Pass trusted server identity through the policy, or remove the override from the stated contract. Test platform admin with no local role and a local owner with no platform privileges.

**M07 · Discovery skips rooms and can hide additional pages.** room-discovery.service.ts:159–186 returns the popped look-ahead row as cursor, then uses skip=1. For A/B/C at limit two, C appears on neither page. Availability is filtered after fetching the page (215–223), and an empty first page causes StudyRoomScreen to render the empty branch instead of Load More. Recent reads current participant/lease rows (87–119), which normal leave deletes, so it loses a completed visit. Use the last returned cursor, filter in the query and derive recent visits from durable history. Verify all room IDs across pages, including a full first page and an immediately departed user.

**M08 · Ordinary idle use has avoidable per-tab and per-event database work.** At 15-second roster polling plus 30-second lease renewals, an uninterrupted foreground tab schedules **240 full roster GETs + 120 renewal POSTs per hour**. One hundred steady tabs schedule **36,000 requests/hour**, including **12,000 lease upserts/hour**, before authentication, subscriptions, join, focus, goals, chat, retries or outbox work. Roster requests read eligibility, participants, users, leases and controllers even when nobody changes (studyroom.service.ts:187–279). With N members, each membership event can additionally cause roughly N full roster requests returning roughly N member records. Waiting for an event when healthy and coalescing roster repairs offers a direct saving. Keep bounded fallback and server expiry. Measure the cost per occupied seat-hour and per room-hour under quiet and high-churn workloads.

**M09 · The unused cleanup routine would also generate unnecessary writes and broadcasts.** studyroom.service.ts:955–990,1049–1105 accepts batchSize but scans all participants and active leases, then visits every room, recomputes count, writes and emits even when unchanged. Merely scheduling it would amplify M08. Delete expired leases in bounded batches, recompute only affected rooms and publish changes only. Verify idle rooms cause zero room writes/events and two workers cannot evict renewed presence.

**M10 · Chat history can overwrite newer live messages.** useRoomChat.ts:65–82 replaces the list with fetched history plus pending messages. A publication arriving between the history snapshot and the HTTP response is already marked sent and disappears. The same hook ignores reaction envelopes with messageId but no id (107–122, compared with messaging/interaction.service.ts:303–324). Merge by canonical ID/sequence, reconcile event types explicitly, and verify delayed history, duplicate publications and reconnect on two clients.

**M11 · Legacy catalog and current creation use different listing values.** Unparameterized GET in route.ts:99–128 filters PUBLIC, includes participant user IDs, and has no OPEN predicate. New rooms and the schema default use LISTED. The legacy result is publicly cached. The legacy seeder explicitly creates PUBLIC rows (src/server/infrastructure/db/postgres/repositories/studyRoom.repo.ts:25–33), which current discovery excludes. Current listed rooms disappear for legacy consumers, and any retained PUBLIC rows can expose closed-room metadata and identities. This exposure requires matching rows; their existence in production is unknown. Share the current listing/status rules and return a minimal public DTO. Check both historical and current fixtures.

**M12 · A partially failed join has no dependable recovery.** On a transient bootstrap or join failure, useRoomOrchestration.ts:193–206 enters reconnecting. Its renewal interval exits when generation is null (254–266), so the failed initial join is never retried by that loop. RoomScreen.tsx:97–101 treats joining/reconnecting as participating and can start secondary requests before admission. Separate initial retry from established lease renewal, gate protected children on confirmed membership and test a failed first request followed by network recovery.

**M13 · Saving one draft disables the next create form.** CreateRoomModal.tsx:31,76,99–116 sets isSubmitting before the request and clears it only on errors. A successful draft closes the modal and stays in discovery. StudyRoomScreen keeps the component mounted, so opening it again preserves isSubmitting=true and the disabled controls (CreateRoomModal.tsx:334–352). Reset submission state on completion and initialize a fresh form for the next room. Save two distinct drafts consecutively without leaving the directory or reloading it.

## Evidence and remaining release checks

- **Existing tests.** From repository root, ran `node_modules/.bin/vitest.cmd run studyroom --maxWorkers=4 --reporter=json --outputFile=.tmp/studyroom-nov5-results.json`. Result: 65 files, 559 passed, zero failed or pending. Includes UI, policy, room services, route contracts, messaging and phase-labelled scenarios. The Phase 12 E2E suite substitutes array-backed database delegates. The load engine generates random latency samples (studyroom-benchmark-engine.ts, roughly lines 190–252). Those figures cannot establish throughput, delivery latency or cost.
- **Additional reproductions.** Ran `node_modules/.bin/vitest.cmd run --config .tmp/studyroom-audit-nov5/config.mts --reporter=verbose`. Ten assertions observed the failure conditions in H01 (two), H02, H03 (two), H04, H07, H08, H09 and M04. React used jsdom and the real provider/registry in H01, with the socket driver stubbed. Route tests called real Next handlers with test identities and isolated database fixtures. H02 checked the exact database predicate as well as the returned row. These reproductions exercised no external accounts or services. Remaining findings are source traces, including the stated concurrency assumptions.
- **Implementation strengths worth preserving.** Creation provisions related records in one DB transaction. A valid join assigns a generation and distinct users determine capacity. Ordinary kick/ban deletes presence/leases and emits a durable left event in the same transaction. Normal room/chat subscribe and sub-refresh verify room status, generation, cohort membership and unexpired lease (`src/server/domain/messaging/proxy-auth.service.ts:183–320`, `infra/centrifugo/centrifugo.config.json`). Chat message creation records a durable event and delivery with a client request ID (`src/server/infrastructure/db/postgres/repositories/messaging.repo.ts:165–220`). The subscription registry can share a physical subscription among handlers when its lifecycle is stable. Sprint countdown ticks normally run locally.
- **Architecture and cleanup coverage.** The production stage uses useRoomOrchestration. The older useRoomLifecycle hook has no production caller found in the source search. Its isolated tests do not establish that the actual stage is fenced. Duplicated control policy and room resolution have demonstrated costs in H08/H09. Memory describes multiple historical implementations; findings above use executable source. No deletion is proposed on the strength of a text search alone.
- **Cost boundaries.** Estimates assume timers run at their specified intervals, one joined tab per seat and no browser throttling. Add per-event fan-out, database/HTTP billing model, websocket connection-minutes, subscription refreshes (proxy expiry 120 seconds), outbox worker/Redis uptime, payload size and retransmission for a real bill. No provider prices, target budget, production usage distribution or billing export were supplied. Personal Web Audio synthesis and per-second countdown rendering do not ordinarily require a server call each tick. Minimal cost has not been established.
- **Live infrastructure and release boundary.** No full-stack cold start, external revocation timing, mobile sleep/wake, browser rendering/accessibility pass, real parallel PostgreSQL run, migration/backfill verification on historical data or production billing inspection was completed. The Docker CLI could not reach the Linux engine. No production credentials were used to work around this. Check schema/index deployment from `prisma/sql/messaging/`, running messaging worker/outbox lag, socket URL/proxies and lease reconciliation scheduling in an isolated deployment. Particularly test whether an already subscribed, modified client continues receiving publications between ban and sub-refresh. A UI denial alone cannot establish socket revocation.

## Correction order and acceptance gate

1. **Protect private reads and writes first.** Close H02–H04, H08 and H13. Repeat the role matrix against direct HTTP and subscription requests, including expired and banned accounts. Assert both response status and exact fields returned. Verify quota and ban controls cannot be bypassed with an unrecognized enum or retained role.
2. **Restore a dependable entry path.** Resolve H01, H05–H07, H09, H14 and M12. In two clean browser profiles create a draft, publish, share, enter, delegate and transfer. Exercise cold navigation and dashboard navigation. Record both clients' roles, capabilities and views after each step without reload.
3. **Make concurrent outcomes authoritative.** Close H10–H11 and M01–M02 with real PostgreSQL sessions. Race last seat, close/join, same-account switch, two owners' settings pages and accept/cancel. Require one valid committed outcome and one corresponding audit/event sequence. Replay the same create after dropping its response.
4. **Verify peer convergence.** Close H12 and M03–M07/M10–M11. Publish/hide a goal, change/clear scene and sound, send/retry a message, start/pause a group sprint, kick, ban and unban. Disconnect B during each change and reconnect it after A goes quiet. Compare both UIs with the authorized snapshot, also on a second app instance. Keep private goals, personal mute, tasks and personal timers isolated.
5. **Measure actual cost.** Address M08–M09. With 2, 10 and 50 independent clients, measure quiet room-hours, steady chat, bursts of simultaneous joins, repeated role changes and crash/expiry. Record API and SQL calls by operation, subscription churn, bytes, event latency percentiles, outbox age, DB CPU and actual billed units. Compare at equal occupancy and delivery latency. Set a seat-hour budget and revocation/delivery targets before claiming acceptance.
